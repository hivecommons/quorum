# Quorum contracts

Three boundaries, versioned together. Every component in hive, quorum and spektacular builds against this file. Version: `quorum.contract/v1`.

## Process model

Quorum runs **inside the hive container** as a child process that hive starts and supervises, the same way hive runs the `spektacular` binary. It listens on loopback only. No extra container, no pod spec change, no hub change.

- Binary: `quorum serve` (Node 22, published as `@hivecommons/quorum` and baked into the hive image).
- Listen: `QUORUM_LISTEN` (default `127.0.0.1:8765`). MCP endpoint `POST /mcp` (streamable HTTP). Health `GET /healthz`.
- Auth: bearer token from `QUORUM_TOKEN_FILE`, generated by hive per boot and passed to the child.
- Vexa: `QUORUM_VEXA_URL` (gateway base URL), `QUORUM_VEXA_API_KEY_FILE` (tenant key; hive writes it from its keystore).
- Discord: `QUORUM_DISCORD_TOKEN_FILE` (per-hive bot token, optional; Discord tools return `platform_unavailable` without it).
- Whisper for Discord audio: `QUORUM_TRANSCRIBE_URL` (the shared CPU transcription service), optional `QUORUM_TRANSCRIBE_TOKEN_FILE`. Each request sends the bot's display name (and its first word) plus `QUORUM_TRANSCRIBE_HOTWORDS` (comma-separated vocabulary; default `Betty, leave, hive, hive queue, pull request, PR, issue, board pressure, crux, dibs, docs, homebrew-hive, hotshot, pluk, promptargs, rationguard, quorum, vexa, quorum-companion, Kubernetes, KubeCon, CNCF, Spektacular, Spek, Plaud, RFC, inbox, spoke, hub`) as the Whisper `prompt`, and each name's first word as `hotwords` (a service without that field ignores it), so the bot's own name is spelled right. A request answered 429 or 5xx, or never answered, is retried up to `QUORUM_TRANSCRIBE_MAX_ATTEMPTS`=4 tries in all, with exponential backoff and full jitter from `QUORUM_TRANSCRIBE_BACKOFF_BASE_MS`=250 capped at `QUORUM_TRANSCRIBE_BACKOFF_MAX_MS`=4000 (a `Retry-After` is honoured up to that cap); only then is the segment dropped, logged with the attempt count. One speaker's segments are transcribed in order. Before a Discord segment is sent, its leading and trailing silence is cut (20 ms frames below `QUORUM_DISCORD_VAD_THRESHOLD`=500 RMS on the int16 scale, 200 ms kept each side); a segment with less than `QUORUM_DISCORD_MIN_SEGMENT_MS` of speech left is not sent. While the service is busy, a speaker's waiting segments are merged into one request (up to `QUORUM_DISCORD_MAX_SEGMENT_S` of audio) rather than queued one request each.
- Speech on Discord: `QUORUM_TTS_URL` (the shared Kokoro service, OpenAI-compatible `/v1/audio/speech`), optional `QUORUM_TTS_TOKEN_FILE` (sent as `X-API-Key`), `QUORUM_TTS_VOICE` (default `af_heart`), `QUORUM_TTS_TIMEOUT_MS`=30000 per request. Without `QUORUM_TTS_URL`, Discord `say` returns `platform_unavailable`. Synthesized sentences are kept for reuse, keyed by voice and text and shared by every meeting, up to `QUORUM_TTS_CACHE_MAX_BYTES`=33554432 of 24 kHz mono PCM (least recently used dropped first); `say.prewarm` fills that cache, at most `QUORUM_SAY_PREWARM_MAX_LINES`=32 lines a call.
- Leaving: `meeting.leave` first waits up to `QUORUM_LEAVE_DRAIN_TIMEOUT_MS`=8000 for speech and chat already on their way (0 turns the wait off). On Vexa a spoken line's playback record is read every `QUORUM_SAY_POLL_MS`=200.
- Companion (desktop app audio, hivecommons/quorum-companion): always registered; needs `QUORUM_TRANSCRIBE_URL` (else `meeting.join` answers `platform_unavailable`). Limits: `QUORUM_COMPANION_MAX_CHUNK_BYTES`=131072, `QUORUM_COMPANION_SILENCE_MS`=500, `QUORUM_COMPANION_EARLY_MS`=100 (0 turns early transcription off), `QUORUM_COMPANION_MIN_SPEECH_MS`=300, `QUORUM_COMPANION_MAX_SEGMENT_S`=20, `QUORUM_COMPANION_VAD_THRESHOLD`=500 (frame RMS on the int16 scale), `QUORUM_COMPANION_OUTBOX_MAX`=200.
- Typed chat on Discord needs the privileged MessageContent intent, which the operator enables for the bot in the Discord developer portal. If Discord refuses it, quorum logs a warning once and connects without it: voice, transcripts and `chat.post` keep working, and no typed `chat` events arrive.
- Every numeric limit in this file is an env var with the default shown.

## 1. Quorum MCP tools (hive is the client)

All tools return `{ok: true, ...}` or `{ok: false, error: {code, message}}`, as MCP `structuredContent` and as the JSON text of the first content item; `isError` is true when `ok` is false. Error codes: `invalid_argument`, `not_found`, `platform_unavailable`, `blocked` (meeting refuses guest bots), `lobby_timeout`, `not_live`, `rate_limited`, `upstream_error`.

| Tool | Arguments | Result |
|---|---|---|
| `meeting.join` | `{url, display_name, platform?, voice?, voice_id?}` platform inferred from URL: `google_meet`, `teams`, `zoom`; a Zoom join always sends Vexa `meeting_url` (the https join link, passcode included; `https://zoom.us/j/<id>` for a bare id), which Vexa requires for Zoom; Zoom on an organisation's own domain (`/j/<id>` or `/meeting/<id>` with a passcode) is accepted only for hostnames in `QUORUM_ZOOM_HOSTED_DOMAINS` (default `zoom-lfx.platform.linuxfoundation.org`; comma-separated, `*.suffix` matches subdomains, empty turns it off), https on port 443 only, no URL credentials, never an IP literal or `localhost` (behavior change: any host was accepted before); Discord uses `{platform:"discord", guild_id, channel_id}`; the companion uses `{platform:"companion", display_name, host_name?}` (no url; every join starts a new meeting, live at once; `host_name`, at most 100 characters, default `Host`, names the `mic` channel's speaker). `voice` (default `QUORUM_VEXA_VOICE`=false) starts the bot able to speak; Vexa fixes this at join time; Discord ignores it (it can speak whenever `QUORUM_TTS_URL` is set). `voice_id` (optional, at most 100 characters) picks the TTS voice for this meeting's `say`: on Discord the Kokoro voice (default `QUORUM_TTS_VOICE`), on Vexa the `voice` sent with each speak request (Vexa's TTS default when absent). Joining a meeting quorum is already in returns that meeting (and keeps its original `voice_id`). | `{meeting_id, platform, state}` |
| `meeting.leave` | `{meeting_id}` | `{state}`. The bot leaves once what it was already saying has been delivered, waiting at most `QUORUM_LEAVE_DRAIN_TIMEOUT_MS`=8000 (0: no wait), so a last "Leaving now." is heard and posted. On Discord it waits for the queued speech to finish playing. On Vexa it waits for the meeting's `say` queue to settle and for the delivery record of the last `chat.post` line that was sent without `confirm` (a line sent with `confirm:true` was already awaited). When the wait runs out the bot leaves anyway and what was still queued is dropped. If the meeting ends by other means during the wait, its state and reason stand. Discord's `/hive leave` command and `meeting.delete` stop at once, without the wait. |
| `meeting.status` | `{meeting_id}` | `{state, participants:[{id,name}]}` |
| `transcript.read` | `{meeting_id, after_seq?}` | `{segments:[Segment], next_seq}` final segments only, oldest first; `next_seq` is the cursor to pass back as `after_seq` |
| `chat.post` | `{meeting_id, text, confirm?}` text max `QUORUM_CHAT_MAX_CHARS`=2000 | `{posted_at, delivery}`. `delivery` is `confirmed` when the platform reports the line in the meeting, else `unconfirmed`. Without `confirm` quorum does not wait: Discord answers `confirmed` (its send returns once the message exists), Vexa `unconfirmed` (the bot only received the line). With `confirm:true` on Vexa, quorum reads the send's delivery record (`GET /bots/{platform}/{native_id}/chat/{request_id}`) every `QUORUM_CHAT_CONFIRM_POLL_MS`=500 for up to `QUORUM_CHAT_CONFIRM_TIMEOUT_MS`=30000 (the Teams bot alone may wait 10 s for the chat composer after admission): `confirmed` once the bot reports it posted, `platform_unavailable` (message names the bot's reason, for example `no_composer` when the meeting chat is not open to the bot) when it reports the send failed, and `unconfirmed` when no verdict came in time or Vexa has no delivery route. A caller that must know the line was seen (the consent notice) passes `confirm:true` and treats `unconfirmed` as not posted. |
| `say` | `{meeting_id, text}` text max `QUORUM_SAY_MAX_CHARS`=1000 | `{queued:true, duration_ms?, first_audio_ms?, synth_ms?, cached?}`. Lines of one meeting play one after another, never over each other. On Discord a line is spoken sentence by sentence: the text is cut at `.`, `!`, `?` or `:` followed by whitespace (a closing quote or bracket stays with its sentence; pieces under 24 characters are joined to a neighbour; text with no such break is one sentence), the sentences are synthesized one after another, and each is queued for playback in order as soon as it is ready, so the first sound comes after one sentence's synthesis. The call resolves once the first sentence is ready (playback is queued behind earlier lines). If the first sentence cannot be synthesized the call answers `upstream_error` and nothing of that line is spoken; a later sentence that fails is skipped and logged, and the sentences after it still play. Each sentence's clip gets a 5 ms fade in and out and is cached by voice and text. `duration_ms` (whole milliseconds) is the line's real audio length when known: on Discord only when every sentence was ready by the time the call resolved (a one-sentence line, or a line whose sentences were all cached), on Vexa when the bot reports it. `first_audio_ms` is the time from the request to the first audio: on Discord until the first sentence was handed to the playback queue; on Vexa the bot's own `first_audio_ms` when the playback record has it, else the time until quorum first read the record as `speaking` or `spoken` (late by at most one poll), present only when the line was reported `spoken`. `synth_ms` is the synthesis time before the first audio: on Discord 0 when the whole line came from the cache, else equal to `first_audio_ms`; on Vexa the record's `synth_ms` when it has one. `cached` says every sentence of the line came from the clip cache (Discord), or is the record's `cached` when it has one (Vexa). On Vexa each say is sent only after the meeting's previous say settled; when the speak answer carries a `request_id`, quorum reads the line's playback record (`GET /bots/{platform}/{native_id}/speak/{request_id}`, statuses `queued`, `speaking`, `spoken` with `duration_ms` and, from a bot that reports them, `first_audio_ms`, `synth_ms` and `cached`, `failed` with `reason`) every `QUORUM_SAY_POLL_MS`=200 for up to `QUORUM_SAY_CONFIRM_TIMEOUT_MS`=60000 and resolves once it is `spoken` (or with no verdict in time, or no such route). `platform_unavailable` when the bot was started without voice or Vexa refuses speech (404/409, message `speak is not available: <detail>`), when the bot reports the line `failed` (message `the line was not spoken: <reason>`, for example `mic_muted`), or when `QUORUM_TTS_URL` is unset (Discord); `upstream_error` when the TTS service fails on the line's first sentence (Discord) |
| `say.prewarm` | `{meeting_id, texts}` `texts` is 1 to `QUORUM_SAY_PREWARM_MAX_LINES`=32 non-empty strings, each at most `QUORUM_SAY_MAX_CHARS` (else `invalid_argument`); the meeting must be live (else `not_live`) | `{queued}`. Gets fixed lines (an introduction, acknowledgements, a goodbye) ready so a later `say` of the same text starts at once. On Discord each line is cut into sentences as `say` does and every sentence not yet cached is synthesized in the background with the meeting's voice, one request at a time; `queued` is the number of sentences sent for synthesis (0 when all were ready or already on their way). A sentence that fails is skipped and synthesized when it is said. Nothing is played. `queued` is 0 on platforms without their own synthesis in quorum: Vexa (its bot synthesizes), the companion, and Discord without `QUORUM_TTS_URL`. |
| `meeting.delete` | `{meeting_id}` | `{deleted:true}` erases transcript upstream |

Live streaming: hive opens `GET /events?meeting_id=...` (Server-Sent Events, same bearer) and receives one JSON object per event. The stream starts with the meeting's current `state` event; `after_seq=N` first replays buffered segment and chat events after N; the SSE `id` is the event's `seq`. Without `meeting_id` the stream carries every meeting's events and starts with the current state of each meeting that has not ended.

- `{"type":"segment", "meeting_id", "seq", "speaker":{id,name}, "text", "start", "end", "final"}`
- `{"type":"chat", "meeting_id", "seq", "author":{id,name}, "text", "at"}` On Discord these are lines people type in the voice channel's built-in text chat (only that channel; bots, webhooks and quorum's own posts are skipped), with `author.id` = the Discord user id.
- `{"type":"state", "meeting_id", "state", "reason?"}` where `state` is one of `requested, joining, lobby, live, ended, failed, blocked`. A `requested` event raised from the platform (Discord `/hive join`) also carries `platform`, `guild_id`, `channel_id` and `requested_by:{id,name}`; hive approves it by calling `meeting.join` for that channel (same `meeting_id`) or declines it with `meeting.leave`.

`seq` is one counter per meeting shared by segment and chat events. `start` and `end` are seconds from the session start. On Vexa platforms `speaker.id` is the display name (Vexa carries no stable participant id); on Discord it is the user id.

`Segment` = the `segment` event without `type`.

### Companion audio

A companion meeting has no bot in any meeting: a desktop app on a person's own computer captures their meeting client's audio and their microphone, and hive relays it to quorum. Both routes take the same bearer as `/events`.

- `POST /companion/audio?meeting_id=&channel=call|mic&seq=N`, body = raw 16 kHz mono s16le PCM, at most `QUORUM_COMPANION_MAX_CHUNK_BYTES`. Per channel, chunks are accepted in order from `seq=0`: a gap answers 409 `{error, expected_seq}`; a chunk at or below the last stored seq answers 200 `{seq, duplicate:true}` and is ignored (a resend after a lost reply); otherwise 200 `{seq, duplicate:false}`. 400 for a bad channel, seq or odd byte count, 404 for an unknown meeting, 409 once the meeting is no longer live, 413 for a chunk over the limit.
- Each channel is cut into utterances at `QUORUM_COMPANION_SILENCE_MS` of silence (or at `QUORUM_COMPANION_MAX_SEGMENT_S`), utterances under `QUORUM_COMPANION_MIN_SPEECH_MS` of speech are dropped, and each one is transcribed by the shared service, one at a time per meeting. Final segments are ordinary `segment` events: `speaker` is `{id:"host", name:<host_name>}` for `mic` and `{id:"call", name:"Call"}` for `call` (the meeting client mixes everyone else). `meeting.leave` transcribes any open utterance before the `ended` state.
- Early transcription: the end of an utterance is only known once `QUORUM_COMPANION_SILENCE_MS` of silence followed it, and the companion sends audio in chunks, so quorum does not wait for it. As soon as an open utterance with at least `QUORUM_COMPANION_MIN_SPEECH_MS` of speech is followed by `QUORUM_COMPANION_EARLY_MS`=100 of silence, it is transcribed ahead of its end, with one attempt (no retries) and at most once per pause. The clip sent is the utterance so far padded with digital silence until its trailing silence is `QUORUM_COMPANION_SILENCE_MS` long, the clip the utterance would be sent as once it ended (a clip that stops right after the last word makes Whisper invent a continuation). If the answer arrives while the utterance is still open and unchanged, it is published as a draft segment (`final:false`), so draft segments now also appear on companion meetings. When the silence then runs its full length with no more speech, the same answer becomes the final segment (`final:true`, the same text) without a second request. If the speaker carries on, the early answer is dropped and the utterance is transcribed whole when it ends, as it is when the early request failed. A draft is never published after its final. `QUORUM_COMPANION_EARLY_MS`=0 turns this off: every utterance is transcribed once, when it ends.
- Every final companion segment logs one info line `companion: segment timing` with `seq`, `channel` (`call` or `mic`), `clip_ms` (the utterance's length), `capture_ms` (the last speech sample to the arrival of the chunk holding it: the companion's chunking and the network), `endpoint_ms` (that arrival to the end of the utterance being known), `stt_ms` (the transcription request that gave the text), `total_ms` (the last speech sample to the segment event) and `early` (true when the text came from the early transcription, so `stt_ms` overlapped the wait for the end).
- `chat.post` queues the line for the companion window instead of a meeting chat. `GET /companion/outbox?meeting_id=&after=N` returns `{lines:[{seq,text,at}], next_seq}`; fetching lines marks them delivered, so `chat.post` with `confirm:true` answers `confirmed` once the companion fetched the line and `unconfirmed` after `QUORUM_CHAT_CONFIRM_TIMEOUT_MS`. Without `confirm` it answers `unconfirmed`. The outbox keeps the last `QUORUM_COMPANION_OUTBOX_MAX` lines.
- `say` answers `platform_unavailable` (spoken replies through a virtual microphone are a later step); `say.prewarm` answers `{queued:0}`. The companion's own consent prompt is the consent gate for these meetings; hive records it.

## 2. Spektacular live mode (hive runs it as a child)

`spektacular meeting --from stdin --format jsonl --title <t> --context <dir>`

One JSON object per line in both directions. Unknown fields are ignored; unknown `type` values are logged and skipped.

stdin (hive to Spek):

- `{"type":"segment", ...}` exactly the Quorum segment event (only `final:true` segments are sent)
- `{"type":"chat", ...}` meeting chat lines from people
- `{"type":"answer", "qid", "text", "by"}` a reply hive matched to an earlier `ask`
- `{"type":"research_update", "rid", "status":"queued|running|done|failed", "summary?", "url?"}`
- `{"type":"end"}` meeting over; Spek flushes notes and exits 0

stdout (Spek to hive, called intents):

- `{"type":"chat.post", "text"}`
- `{"type":"ask", "qid", "text"}` a clarifying question; hive posts it and routes the next reply as `answer`
- `{"type":"notes.append", "section", "text"}` sections: `decisions`, `actions`, `questions`, `summary`, `notes`
- `{"type":"research", "rid", "query", "reason"}`
- `{"type":"say", "text"}` only when the meeting addressed hive by name; hive decides whether voice is allowed
- `{"type":"heartbeat"}` at least every `SPEK_MEETING_HEARTBEAT_S`=15 seconds

Spek never calls Quorum directly. Hive is the policy point: budgets, rate limits, voice rules and consent are enforced in hive before anything reaches the meeting.

Behaviour targets: act on final segments only; ask at pauses longer than `SPEK_MEETING_PAUSE_MS`=1500; at most `SPEK_MEETING_MAX_ASKS_PER_10M`=3 questions per 10 minutes; never repeat a question; "hive, research X" and close variants are explicit research; implicit mentions ("we should look into X") become an offer via `chat.post` and only become `research` after someone agrees.

## 3. Hive meeting API and research return

- `POST /api/meetings {url | platform+guild_id+channel_id, voice?:bool}` owner-only, returns the meeting record.
- `GET /api/meetings`, `GET /api/meetings/{id}`, `POST /api/meetings/{id}/leave`, `POST /api/meetings/{id}/voice {enabled}`, `POST /api/meetings/{id}/research/{rid}/approve`.
- `GET /api/meetings/{id}/ws` live panel: transcript, intents, research status.
- Research: each `research` intent becomes a kick to the research agent pool with a kick ID; `[FINDING]` and `[COMPLETE]` signals for that kick come back as `research_update` to Spek and a `chat.post` summary (max one per research item) plus a knowledge fact under the meeting's notes.
- On join hive posts the consent notice (`meetings.consent_text`) before anything else. `hive leave` typed in chat or said to hive makes it leave.
